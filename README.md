# newstats

Собственная БД статистики и аналитические скрипты для ставок, построенные
над выводом внешнего скрапера
[M3MONs/FlashscoreScraper](https://github.com/M3MONs/FlashscoreScraper).
Скрапер — отдельный проект, его код сюда не копируется и не форкается; этот
репозиторий только читает его JSON-вывод с stdout.

## Как реально работает скрапер (важно для интеграции)

`FlashscoreScraper` — CLI на один URL матча за раз, без собственных файлов
вывода — печатает один JSON-объект в stdout на вызов:

```bash
python main.py event      <match_url>                                   # базовая инфа + счёт + статус
python main.py odds       <match_url>                                   # коэффициенты (вызов на каждый тип рынка)
python main.py event-info <match_url>/standings/standings/overall/      # таблица лиги
python main.py event-info <match_url>/draw/                            # сетка плей-офф (пока не импортируется)
```

В нём **нет** данных по игрокам и **нет** детальной командной статистики
матча (владение, угловые и т.п.) — таких полей скрапер не выдаёт. Счёт и
статус — свободный текст (`"2 - 1"`, `"Finished"`), не готовые числа/enum.
ID матча не передаётся явным полем — это `?mid=...` в самом URL, который вы
скрейпили.

Наш импортёр (`newstats/importer/flashscore.py`) — это адаптер именно под
эту реальную форму вывода, не под придуманный контракт. Если формат
скрапера поменяется, править нужно только этот файл.

## Данные, которых у FlashscoreScraper нет (составы, угловые, карточки)

У самого FlashscoreScraper нет и не будет: игроков, голов по игрокам,
угловых/штрафных/карточек — на сайте это не часть `event`/`odds`/`event-info`
выдачи, а отдельные вкладки страницы матча (`Summary` — таймлайн событий,
`Stats` — командная статистика), которые рендерятся JS и требуют прямого
скрейпинга HTML, а не CLI-инструмента.

Для этого в `newstats/importer/flashscore.py` есть ещё два импортёра,
рассчитанные на такой прямой скрейп (не на вывод `main.py`):

- `ingest_match_stats(session, match_url, stats)` — командная статистика
  матча (угловые, штрафные, владение, удары и т.д.) со страницы
  `<match_url>/summary/stats/overall/`. Ожидает
  `[{"label": "Corner kicks", "home": "2", "away": "5"}, ...]`.
- `ingest_match_events(session, match_url, incidents)` — события матча
  (голы, передачи, жёлтые/красные карточки) с таймлайна на самой странице
  матча. Ожидает
  `[{"type": "goal"|"assist"|"yellow_card"|"red_card", "side": "home"|"away",
  "player_name": "...", "player_link": "/player/.../..."}, ...]`. Голы одного
  игрока агрегируются в одну строку (`stat_name="goals"`, `value=2` при дубле),
  не создают дубликаты.

CLI: `newstats ingest-stats-cmd <url> --file ...` и
`newstats ingest-events-cmd <url> --file ...` — тот же `--file`/stdin
паттерн, что и у остальных команд.

Пример скрейпера под эту форму (Playwright + BeautifulSoup, не трогает код
FlashscoreScraper) — `scripts/collect_match_details.py`.

## Скрипты массового сбора (`scripts/`)

```bash
uv pip install -e ".[scraping]"
python -m playwright install chromium
```

- `scripts/collect_cl_teams.py` — для списка команд (сейчас зашит на 36
  команд лиги чемпионов 2026/27, но список в начале файла можно заменить
  на любой) находит последние N матчей каждой команды **во всех турнирах**
  через их страницы `/team/<slug>/<id>/results/`, прогоняет каждый
  уникальный матч через настоящий парсер `FootballEventParser` из
  клона `M3MONs/FlashscoreScraper` и грузит в БД через `ingest_event`.
  Требует `FLASHSCORE_SCRAPER=/path/to/FlashscoreScraper` (с его
  собственным venv, playwright-браузерами и зависимостями).
- `scripts/collect_match_details.py` — второй проход по уже загруженным
  матчам: досчитывает `kickoff_at`, тянет командную статистику
  (`ingest_match_stats`) и события матча/голы/карточки
  (`ingest_match_events`) напрямую с HTML страниц матча.

Оба — asyncio + Playwright, идут по 5 страниц одновременно, идемпотентны
(повторный запуск просто обновляет те же строки, не плодит дубли).

## Прогноз (xG-модель) и бэктест

`newstats/stats/xg_model.py` — простая пуассоновская модель по среднему
xG команды за/против (не Диксон-Коулз, не подгонка, осознанно минимальная
отправная точка). `newstats/stats/value_bets.py` — сравнение модели с
девигованными коэффициентами букмекеров.

```bash
newstats predict <home_team_id> <away_team_id>
newstats value-bets <match_id>   # нужны уже загруженные через ingest-odds-cmd коэффициенты
```

Проверка модели на фактических результатах — `scripts/backtest.py`.
Для каждого матча прогноз строится **только на данных до его начала**
(`predict_match(..., before=match.kickoff_at)`), иначе бэктест был бы
нечестным (матч предсказывался бы с учётом собственного же результата).

```bash
DATABASE_URL=... python scripts/backtest.py                              # все матчи в базе
DATABASE_URL=... python scripts/backtest.py --since 2026-10-13 --until 2026-10-14
DATABASE_URL=... python scripts/backtest.py --quiet                      # только сводка
```

Текущий результат на 310 `FINISHED` матчах (311 загруженных минус 1
решённый по пенальти — см. «Известные ограничения»), 2026-08 — 2026-10:
**67/104 (64.4%, 95% ДИ [54.8%, 74.0%])** точных исходов 1X2 против
наивного базлайна «всегда дома» (50.0%), Brier 0.536 [0.444, 0.630] и
log loss 0.942 [0.792, 1.102] — оба лучше равновероятного базлайна
(Brier 0.667, log loss 1.099). Over/Under 2.5: 62.5% точность. 206 из
310 матчей пропущены — это каждая команда до её первого матча с
историей в базе (у нас не полный сезон, а «последние 10 матчей» на
команду, так что для разовых соперников вне ЛЧ истории часто просто
нет). Сравнение с рынком (Δ log loss против девигованных коэффициентов)
пока не считается ни разу — исторических коэффициентов в базе нет
(см. ниже про снапшоты).

**Широкие доверительные интервалы — это буквальный ответ на вопрос «значимо
ли это».** На n=104 ДИ по точности — почти 20 п.п., так что сами числа —
ориентир, не подтверждённая модель. По мере накопления данных (`scripts/
collect_match_details.py` на новые туры) точность модели можно
перепроверять этим же скриптом без правок кода — ДИ будут сужаться.

## Время, снапшоты коэффициентов и CLV

`kickoff_at` хранится в UTC. `parse_kickoff(date, source_tz=...)` и
`ingest_event(..., source_tz=...)` берут исходную таймзону **явным
аргументом**, не из переменной окружения — раньше был единый глобальный
`SOURCE_TZ`, и это было ошибкой: `scripts/collect_*.py` пинят
Playwright на `timezone_id="UTC"` (дата уже в UTC), а ручной вызов
`main.py event` внешнего скрапера без явного `timezone_id` отдаёт дату
в часовом поясе хоста (у нас это оказалось `Europe/Moscow` — см.
«Известные ограничения»). Общая настройка на процесс означала, что
один из двух путей неизбежно получал не ту зону — именно это и
случилось при первом проходе по данным (см. ниже). Теперь оба
`scripts/collect_*.py` передают `source_tz="UTC"` явно; `ingest-event-cmd`
принимает `--source-tz` для ручного пайплайна с другой зоной.

**Разовый пересчёт исторических данных.** Когда баг с таймзоной
обнаружился, `kickoff_at` уже лежал в базе как наивный MSK
(UTC+3, без перевода). Исправлено вручную одним запросом, не миграцией
(это данные одного конкретного прогона, не схема):

```sql
UPDATE matches SET kickoff_at = kickoff_at - INTERVAL '3 hours' WHERE kickoff_at IS NOT NULL;
```

Если разворачиваете `newstats_cl.db`/аналогичную базу заново с текущей
версией кода (`source_tz` передаётся явно) — этот пересчёт не нужен,
даты изначально лягут в UTC правильно. Нужен он только для копии базы,
собранной до этого фикса.

Без фиксации **момента** снятия коэффициентов «модель против рынка» —
просто шум: неизвестно, была эта цена доступна за сутки до матча или
за минуту. `scripts/snapshot_odds.py` берёт коэффициенты в трёх окнах
перед стартом (`t-24h`, `t-1h`, `close`) для каждого матча со статусом
`SCHEDULED` в ближайшие ~25 часов, идемпотентно (повторный запуск не
дублирует уже взятые окна) — рассчитан на cron каждые 5 минут на
постоянно включённой машине (GitHub Actions не подходит: нужен живой
Playwright и доступ к БД, а не разовый CI-джоб):

```bash
*/5 * * * * cd /path/to/newstats && \
    FLASHSCORE_SCRAPER=/path/to/FlashscoreScraper DATABASE_URL=... \
    .venv/bin/python scripts/snapshot_odds.py >> snapshot_odds.log 2>&1
```

CLV (closing line value) для ставки по цене `o` на исход, чья
де-виг­ованная вероятность на закрытии — `p_close`: `clv = o·p_close − 1`
(`newstats.stats.value_bets.clv`). Положительное значение — цена была
лучше закрытия, независимо от того, зашла ставка или нет.

`scripts/simulate_bets.py` ставит по цене конкретного снапшота
(`--snapshot t-1h` по умолчанию, можно `t-24h`) и требует, чтобы у
матча была **и** эта цена, **и** `snapshot="close"` — без обеих ставка
не считается. Ставить по самому `close` нельзя: де-виг `close`-цены —
это (с точностью до маржи букмекера) и есть рыночная вероятность на
закрытии, так что "эдж" против неё — не сигнал, а просто минус маржа.
Прогноз модели для каждой ставки считается с `before=` временем
**снапшота** (`newstats.stats.value_bets.snapshot_recorded_at`), а не
временем начала матча — иначе модель видела бы данные, которых ставка
"в прошлом" видеть не могла.

```bash
newstats_venv/bin/python scripts/simulate_bets.py --snapshot t-1h --book bet365 --ev-min 0.05
```

На текущих данных — 0 ставок: исторических снапшотов нет, их должен
накопить `scripts/snapshot_odds.py` за несколько недель работы.

## Результаты бэктеста (walk-forward, на 307 matches со `status_raw == "Finished"`, n=102 скор.)

Каждое изменение модели прогоняется тем же `scripts/backtest.py` до и
после, без переподбора порогов задним числом. На n≈100 различия внутри
ДИ почти никогда не значимы — из равных вариантов остаётся более простой.

Первые три строки таблицы посчитаны ещё до того, как фильтр матчей был
ужесточён с `MatchStatus.FINISHED` до `status_raw == "Finished"` (п. 3,
исключение `"After Extra Time"` — см. «Известные ограничения»): тогда
было n=104 на 310 матчах, сейчас n=102 на 307. Разница — 2 матча на
n≈100, числа сдвигаются на уровне третьего знака, ни один вывод ниже от
этого не меняется; **последняя актуальная проверка на текущем фильтре —
строка «+ shrinkage, пересчитано»**.

| версия | logloss | Δ к пред. версии | Brier | Over2.5 acc |
|---|---|---|---|---|
| baseline (asymmetric `home_adv`, только `lambda_home` домножался) | 0.942 [0.792, 1.102] | — | 0.536 | 62.5% |
| `expected_goals()` — симметричный home_adv (п. 3) | 0.940 [0.795, 1.094] | −0.002 | 0.536 | 56.7% |
| + shrinkage по `matches_considered`, K=5 (п. 5.1) | 0.920 [0.849, 0.991] | −0.020 | 0.542 | 76.0% |
| opponent-adjusted iterative fit, `--method fitted` (п. 5.2) | 0.996 [0.847, 1.153] | **+0.076, отклонено** | 0.585 | 51.9% |
| + shrinkage, пересчитано на `status_raw=="Finished"` (n=102) | 0.918 [0.848, 0.991] | ≈0 к строке выше | 0.540 | 75.5% |
| opponent-adjusted, пересчитано на том же фильтре (n=102) | 0.989 [0.840, 1.142] | **+0.071, по-прежнему отклонено** | 0.581 | 52.9% |

Сдвиг в logloss/Brier — в пределах шума (ДИ перекрываются почти
полностью), но модель теперь математически корректна для среднего
случая (`(λh+λa)/2 == league_avg`, `λh/λa == home_adv` для равных
команд), а не просто "работала похоже". Over2.5-точность на этой
выборке стала хуже (56.7% вместо 62.5%) — несмещённая модель менее
агрессивна по сумме голов, а в этих конкретных 104 матчах фактическая
доля "больше 2.5" была высокой (76%), так что смещённая версия
случайно оказывалась ближе к этой выборке. Не повод откатывать фикс —
это и есть иллюстрация того, зачем нужен п. 1 (ДИ), а не точечные числа.

**Shrinkage (п. 5.1)** — log loss улучшился заметнее (0.940 → 0.920) и
его ДИ заметно сузился (0.795–1.094 → 0.849–0.991), что соответствует
теории: уменьшение дисперсии у команд с маленькой выборкой матчей.
Accuracy по 1X2 при этом просела (64.4% → 60.6%), **а Brier — тоже
proper scoring rule — слегка ухудшился (0.536 → 0.542)**, то есть не
все метрики согласны. ДИ по всем трём почти полностью перекрываются —
формально значимой разницы нет ни в одну сторону. Over2.5-точность
подскочила до 76.0% — ровно фактическая доля "больше 2.5" в выборке,
то есть модель перестала делать резкие ставки в обе стороны и теперь
ближе к базовой частоте (не признак навыка сам по себе, см. ниже).
Shrinkage оставлен не потому, что он доказанно лучше на бэктесте —
на n=104 это не доказано ни в одну сторону, — а из теории (регуляризация
по размеру выборки — стандартная и правильная вещь) и простоты.

**Opponent-adjusted iterative fit (п. 5.2, `newstats.stats.xg_model.
fit_team_ratings` / `predict_match_fitted`, CLI `--method fitted`)
отклонён как дефолт.** На нашем текущем датасете хуже по всем метрикам
(log loss 0.996 вместо 0.920, Brier 0.585, accuracy 55.8%). Причина не
в коде — проверено вручную на полностью связном трёхкомандном
round-robin (`test_fit_team_ratings_separates_strong_mid_weak_in_a_connected_league`),
там модель корректно разделяет сильных/средних/слабых. Причина — в
данных: **139 из 227 команд в базе встречаются ровно в одном матче**
("последние 10 матчей" на команду означает, что разовые соперники вне
ЛЧ — листья графа, их рейтинг ничем не ограничен, кроме этой одной
игры). Итеративная подгонка на несвязном графе не определена
однозначно — модель с тем же успехом может решить, что "команда
сильная" или что "её немногочисленные соперники слабые". Условие для
пересмотра: когда датасет станет связным (возврат нескольких туров ЛЧ
+ нескольких туров внутренних чемпионатов для всех команд, а не только
последних 10 матчей), `--method fitted` стоит перепроверить тем же
`scripts/backtest.py` — код уже на месте, флаг не нужно переписывать.

**Калибровка (п. 5.3)** — `scripts/backtest.py` печатает 5 корзин по
предсказанной вероятности каждого исхода (home/draw/away в сумме, не
по отдельности — на n=104 на 5 корзин и так мало), сравнивая среднюю
предсказанную вероятность с фактической долей. На текущих данных
(shrinkage-модель):

| корзина | предсказано | факт | n |
|---|---|---|---|
| 0–20% | 16.2% | 3.4% | 29 |
| 20–40% | 27.0% | 23.7% | 186 |
| 40–60% | 49.0% | 57.7% | 78 |
| 60–80% | 67.3% | 91.7% | 12 |
| 80–100% | 81.4% | 100.0% | 1 |

**Важная оговорка про сами корзины**: они пулят три исхода (home/draw/away)
одного матча в независимые наблюдения, но это не независимые наблюдения —
вероятности одного матча в сумме дают 1, так что строгий статистический
тест по корзинам не стоит проводить без поправки на это (кластеризация по
матчу). Числа ниже — описательные, не доказательные.

Средние корзины (20–60%, где основная масса данных, n=264 из 306)
выглядят разумно откалиброванными. Корзина 0–20% — другое дело: n=29,
средний прогноз 16.2% подразумевает ≈4.7 ожидаемых "попадания", реально
случилось 1. Вероятность получить ≤1 при p=16.2% и n=29 (биномиально,
без поправки на кластеризацию) — ≈3.9%. Это не "шум, можно игнорировать"
на уровне ≈5% — модель, похоже, завышает вероятность на нижнем конце.
Не проверено на кластеризацию и не перепроверено на большей выборке,
но и не отбрасывается как случайность. На корзинах 60–80% (n=12) и
80–100% (n=1) выборка слишком мала для любого вывода в любую сторону.

Отдельно: Over2.5 у shrinkage-модели вышел на 76.0% — это ровно
фактическая частота "больше 2.5" в выборке, то есть модель не показывает
навыка в эту сторону, просто не завышает и не занижает average. Сама эта
фактическая частота (76%) необычно высока для футбола (обычно ближе к
половине матчей) — **не проверено**, нет ли систематического смещения в
выборке (например, клубные товарищеские/квалификационные матчи ЛЧ,
которых много в "последних 10" датасете, статистически отличаются от
обычных лиговых игр).

## Схема

```
Sport
  └── Tournament
        ├── Match ── home_team / away_team ──> Team
        │     └── Odds   (история коэффициентов по рынкам/букмекерам)
        └── Standing     (снэпшот таблицы лиги на момент скрейпа)
```

`Player`/`PlayerTeam`/`MatchStat`/`PlayerMatchStat` в схеме оставлены как
задел на случай другого источника данных с составами и детальной
статистикой — текущий флэшскор-импортёр их не заполняет, потому что в
скрапере такие данные просто отсутствуют.

```bash
uv venv --python 3.12

cp .env.example .env   # поправьте DATABASE_URL

```

Пример полного пайплайна «скрапер → наша БД» для одного матча:

```bash
MATCH_URL="https://www.flashscore.com/match/football/team-a-.../team-b-.../?mid=XXXXXXX"

# из каталога FlashscoreScraper
python main.py event "$MATCH_URL" \

```

`ingest-event-cmd` обязателен первым для матча — остальные `ingest-*-cmd`
ищут матч по его `mid` и падают с понятной ошибкой, если матч ещё не
импортирован. **`ingest-odds-cmd` принимает `$MATCH_URL` отдельным
аргументом, а не берёт его из `odds_result["url"]`** — на реальных данных
`FlashscoreUrlBuilder.build_odds_url` обрезает `?mid=` при сборке URL под
конкретный тип коэффициентов, так что этого поля недостаточно, чтобы найти
матч (подтверждено живым запросом, не только по фикстурам).

## Известные ограничения

**Часовой пояс.** `event["date"]` от скрапера — это не UTC и не "время
матча" в абстрактном смысле: Flashscore рендерит его в часовом поясе
*браузера, который его скрейпил* (клиентский JS-рендеринг). Разные
вызовы скрейпились разными браузерами в разных зонах — `scripts/
collect_*.py` сами пинят Playwright на `timezone_id="UTC"`, а ручной
прогон `main.py event` внешнего скрапера без явного `timezone_id`
наследует зону хоста (у нас это оказалось `Europe/Moscow`, UTC+3 —
проверено: матч ЛЧ с официальным киком 21:00 CEST = 19:00 UTC у нас в
`date` дал `22:00`). Поэтому `parse_kickoff`/`ingest_event` берут зону
**явным аргументом `source_tz`**, не из общей переменной окружения —
раньше был единый глобальный `SOURCE_TZ`, и это было ошибкой именно
из-за разницы между этими двумя путями (см. раздел «Время…» про
разовый пересчёт уже накопленных данных, пострадавших от этого).

**Счёт при доп. времени и пенальти.** `detail_status` для решённых в
доп. время матчей — `"After Extra Time"` (не `"After ET"`, как
предполагалось изначально), и `score` в этом случае — это уже итоговый
счёт по итогам **120 минут**. Рынок 1X2 обычно рассчитывается по **90
минутам** — значит 120-минутный счёт для 1X2 годится не всегда (ничья
1:1 после 90, выигранная в доп. время, в данных выглядит как победа
хозяев). Отдельного 90-минутного среза у нас нет, восстановить его из
120-минутного счёта нельзя — поэтому такие матчи **исключаются** из
1X2-бэктеста/ставок (`status_raw == "Finished"` в `scripts/backtest.py`
и `scripts/simulate_bets.py`, а не просто `MatchStatus.FINISHED`).

Для матчей, решённых по пенальти (`detail_status == "After 90
minutes"`), наоборот: `score` — это как раз 90-минутный счёт, корректный
исход для 1X2 (ничья есть ничья, независимо от исхода серии пенальти;
кто формально прошёл дальше — отдельный рынок, не 1X2). Раньше здесь
было написано, что такие матчи исключаются, потому что "неизвестен
исход" — это было неверно: исход для 1X2 известен, неизвестен только
победитель серии пенальти, который к 1X2 не относится. Матч всё равно
исключён тем же фильтром `status_raw == "Finished"`, но не по этой
причине, а просто заодно с ET — на один матч в текущих данных это
ничего не меняет, но если реализовывать строже, различать их стоит.
